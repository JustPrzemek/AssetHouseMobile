UWAGI DO BACKENDU (rfidentity 1.0.6-SNAPSHOT)
=============================================
Data: 2026-08-18
Zrodlo: lokalne uruchomienie backend/rfidentity.war na Tomcat 10.1.31 + PostgreSQL 16.4,
        testowane realna aplikacja mobilna na skanerze Zebra MC3300x (serial 23163523021979).


1. BLAD: nieznany pokoj zwraca 401 zamiast 404
----------------------------------------------
Objaw:
  GET /api/mobile/insideLocation?location=NO_SUCH_ROOM&deviceId=...
  -> HTTP 401, naglowek "www-authenticate: Bearer", content-length: 0

Backend poprawnie wykrywa blad i loguje:
  ERROR [p.m.s.e.GlobalExceptionHandler] - Entity not found:
  jakarta.persistence.EntityNotFoundException: Location 'NO_SUCH_ROOM' not found for inventory ID 1

Przyczyna (wywnioskowana z bytecodu GlobalExceptionHandler.class + zachowania,
NIE ze zrodel - warto potwierdzic w repo backendu):

  handleEntityNotFoundException(EntityNotFoundException) -> ErrorResponse

  zwraca gole ErrorResponse, a nie ResponseEntity. Odpowiedz nie ma ciala
  (content-length: 0), wiec puste 404 jest przekierowywane przez
  Spring Boot ErrorPageFilter na /error. Sciezka /error nie jest w permitAll
  w SecurityConfig, wiec OAuth2 resource server zwraca 401.

  Kontrast potwierdzajacy: handlery uzywajace ResponseEntity/BodyBuilder dzialaja
  poprawnie - np. pusty deviceId zwraca prawidlowo:
  {"statusCode":400,"message":"Device ID is required",...}

Proponowana poprawka:
  handleEntityNotFoundException ma zwracac
  ResponseEntity.status(HttpStatus.NOT_FOUND).body(errorResponse)
  - dokladnie tak jak handler od 400.

  Alternatywa (leczy objaw, nie przyczyne): dodac /error do permitAll w SecurityConfig.

Wplyw na aplikacje mobilna:
  Apka obsluguje 404 jako "nieaktualny inwentarz" i pokazuje komunikat
  z prosba o restart. Dopoki backend zwraca 401, ten komunikat sie NIE pokaze.
  Kod mobilny zostaje zgodny ze specyfikacja (404) - czeka na poprawke backendu.


2. BLAD: brak parametru deviceId zwraca 500 zamiast 400
-------------------------------------------------------
  GET /api/mobile/insideLocation?location=ROOM%20A   (bez deviceId)
  -> HTTP 500
  {"statusCode":500,"message":"Required request parameter 'deviceId' for method
    parameter type String is not present"}

  MissingServletRequestParameterException nie jest zmapowany na 400.

  Uwaga: PUSTY deviceId (deviceId=) dziala poprawnie -> 400 "Device ID is required".
  Chodzi wylacznie o calkowity brak parametru.

  Aplikacji mobilnej to nie dotyczy (zawsze wysyla niepusty deviceId),
  ale kontrakt mowi 400.


3. LIMIT 1000 NA STRONE (do swiadomej decyzji)
----------------------------------------------
  Serwer tnie parametr size do 1000 niezaleznie od zadania:

    size=1000 -> pagination.size=1000, zwrocone 1000
    size=2000 -> pagination.size=1000, zwrocone 1000
    size=5000 -> pagination.size=1000, zwrocone 1000
    (przy totalElements=1201)

  Prawdopodobnie spring.data.web.pageable.max-page-size.

  KONSEKWENCJA: pokoj powyzej 1000 assetow wymaga kilku zapytan, a kazde
  zapytanie to osobny rekord w scanner_activity (log jest append-only).
  Pokoj 1201 assetow = 2 rekordy INSIDE_LOCATION na jedno wejscie.

  To bylo tez zrodlem cichego gubienia danych w aplikacji mobilnej
  (stary kod prosil o size=totalElements i dostawal max 1000) - poprawione
  po stronie apki przez dociaganie kolejnych stron.
